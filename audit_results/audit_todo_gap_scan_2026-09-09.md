## Section 2: Structural gaps

### 1a. Policy-vs-extractor drift — `view_category_overrides_model`/`_annotation` vs. policy (`vco.category_hidden` missing from `allowed_items`)
- **What's missing:** Both `domains/view_category_overrides_model.py` and `_annotation.py` classify `vco.category_hidden` as a `semantic` item and fold it into `identity_items_sorted` — it's part of the extractor's real, authoritative inline `sig_hash`. `policies/domain_sig_hash_policies.json`'s entries for both partitions omit `vco.category_hidden` from `allowed_items` entirely, so it's silently dropped from the analysis-side (`core/sig_hash_builder.py`) hash reconstruction.
- **Why load-bearing:** Two records differing only in hidden-state would produce different real `sig_hash` values but the same policy-reconstructed hash — the exact "silently collapse distinct states" failure CLAUDE.md's Fail-Soft Policy forbids. Same drift class CLAUDE.md documents as already fixed for `wall_types`/`object_styles_model` (D-039/D-042); this domain hasn't been through that reconciliation pass (see Finding 5).
- **Confidence:** high.

### 1b. Policy-vs-extractor drift — `view_category_overrides_annotation` vs. policy (`vco.cut.*` entirely absent from `allowed_items`)
- **What's missing:** `view_category_overrides_annotation.py` unconditionally computes `vco.cut.*` items (via `extract_cut_graphics`) and folds them into `identity_items_sorted` — part of the real inline `sig_hash`. `policies/domain_sig_hash_policies.json`'s `view_category_overrides_annotation.allowed_items` has no `vco.cut.*` keys at all (unlike the `_model` entry, which does list them). `contracts/domain_identity_keys_v2.json`'s `allowed_keys` confirms the same omission at the source-of-truth level — not a compiler artifact of `tools/generate_sig_hash_policy.py`, the registry itself is out of sync.
- **Why load-bearing:** Any cut-graphics-override difference (line weight, color, pattern reference) is invisible to the policy-reconstructed hash even though it changes the real one. Same fail-soft violation as 1a.
- **Confidence:** high.

### 1c. Policy-vs-extractor drift — `view_category_overrides_{model,annotation}` vs. policy (template/UID/context fields declared but never emitted as identity items; one apparent stale rename)
- **What's missing:** `vco.template_name` (cosmetic), `vco.template_element_id`/`vco.template_unique_id` (unknown_items), and `vco.context_type` (coordination_items — the code actually emits `vco.vg_tab`, not `vco.vg_category_type`) are deliberately kept *out* of `identity_items` by both extractor files. Yet `policies/domain_sig_hash_policies.json`'s `allowed_items` for both partitions lists `vco.template_name`, `vco.template_element_id`, `vco.template_unique_id`, `vco.context_type`, plus `vco.vg_category_type` and `vco.include_controlled` — neither of the last two is emitted anywhere in `domains/*.py` under any name; `vco.vg_category_type` looks like a stale name for what the code now calls `vco.vg_tab`.
- **Why load-bearing:** **Resolved 2026-09-10 by static trace (no corpus needed) — these are confirmed inert cruft, not a live hash-correctness bug.** Traced the full flatten→sig_hash path: `domains/view_category_overrides_model.py:347-352` builds `rec["phase2"] = {"cosmetic_items":..., "coordination_items":..., "unknown_items":...}` as a **sibling** key to `rec["identity_basis"]`, never merged into it (`core/record_v2.py:589` confirms `identity_basis` is the standard items container). `tools/extractor.py:1107-1109` (`_flatten_one_file`) sources flatten-stage items *only* from `rec.get("items")` (top-level flat shape, canonical_items.py-migrated domains only) or, falling back, `rec["identity_basis"]["items"]` — `rec["phase2"]` is never referenced anywhere else in that file (its only other `phase2` hits, lines 162-182, are the unrelated `identity`-domain lineage-metadata sub-object). Those items alone become `item_shard_rows` (`extractor.py:1110-1123`), written to `identity_items_by_domain/<domain>.csv` as "the sole identity_items output" (`extractor.py:1298`). The sig_hash stage's `_load_items_for_domain()` (`tools/run_extract_all.py:318-331`) reads exclusively from those same shards before calling `build_sig_hash_from_policy(items=rec_items, ...)` (`run_extract_all.py:349,355-357`), which is where `core/sig_hash_builder.py:29`'s `_key_allowed()` runs. So `vco.template_name`/`vco.template_element_id`/`vco.template_unique_id`/`vco.context_type`/`vco.vg_category_type`/`vco.include_controlled` cannot reach `_key_allowed()` under any circumstances — stale, misleading policy/contract declarations with zero effect on any computed sig_hash. This does **not** extend to Findings 1a/1b (`vco.category_hidden`, `vco.cut.*`), which live in `identity_basis.items` and do flow through this exact pipeline — those remain live, high-confidence bugs.
- **Confidence:** high (resolved from medium; both the bucket-vs-policy mismatch and the non-reachability are now directly traced, not inferred).
