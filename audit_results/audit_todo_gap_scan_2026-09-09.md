## Section 2: Structural gaps

### 1. Policy-vs-extractor drift — `view_category_overrides_{model,annotation}`: view-template name/ElementId/UniqueId leak into the analysis-side sig_hash reconstruction (CONFIRMED LIVE BUG)
- **Correction history, for the record:** this finding went through three states across this audit. (i) 2026-09-09 original: flagged at medium confidence, capped pending a trace of whether phase2-bucketed fields reach the flatten stage. (ii) 2026-09-10 first follow-up: incorrectly "resolved" as inert cruft, based on a static trace of `tools/extractor.py`'s flatten stage alone (`rec.get("items")` or `rec["identity_basis"]["items"]`) that did not account for a *prior*, extraction-time canonicalization step. (iii) 2026-09-10 second follow-up (this entry): a PR review comment (`chatgpt-codex-connector`, PR #484) identified the missed step; verified directly and **reversed** — this is a real, live, high-confidence bug. Keeping this history inline because it's a case study in exactly the kind of trace error this audit exists to catch — the fix was three call frames further up the stack than the first trace looked.
- **What's wrong:** `policies/domain_sig_hash_policies.json`'s `allowed_items` for both `view_category_overrides_model` and `view_category_overrides_annotation` includes `vco.template_name`, `vco.template_element_id`, `vco.template_unique_id`, and `vco.context_type` (confirmed by direct read of the policy file). Both extractor files genuinely emit these keys: `vco.template_name` into `rec["phase2"]["cosmetic_items"]`, `vco.template_element_id`/`vco.template_unique_id` into `rec["phase2"]["unknown_items"]`, `vco.context_type` (value `"template"`) into `rec["phase2"]["coordination_items"]` (`domains/view_category_overrides_model.py:320-353`, mirrored in `_annotation.py`).
- **Full corrected trace (extraction-time, not just analysis-side):** `runner/run_dynamo.py:1154` unconditionally calls `_canonicalize_all_domain_records(fingerprint)` on every domain's records — no feature flag, no domain filter, confirmed by direct grep of the whole file. That function (`runner/run_dynamo.py:1247-1260`) calls `core/canonical_items.py:130`'s `canonicalize_record()` on every single record, which merges `identity_basis.items` **and all of `phase2.semantic_items`/`lineage_items`/`cosmetic_items`/`coordination_items`/`unknown_items`** into one flat top-level `items` list (`canonical_items.py:137-145`, `build_flat_items()`) and then deletes the `identity_basis`/`phase2` keys from the record entirely (`canonical_items.py:149-150`). So by the time the exported JSON reaches disk, `rec["items"]` already contains `vco.template_name`/`vco.template_element_id`/`vco.template_unique_id`/`vco.context_type` alongside the real identity items — there is no separate "phase2 bucket" left to drop, for this or any other domain. `tools/extractor.py:1107-1109` (`_flatten_one_file`) reads that already-merged `rec["items"]` (its `identity_basis.items` fallback is dead code once this canonicalization has run), writes the rows to `identity_items_by_domain/<domain>.csv` (`extractor.py:1280-1298`), and `tools/run_extract_all.py:318-331`'s `_load_items_for_domain()` reads them straight into `build_sig_hash_from_policy(...)` → `core/sig_hash_builder.py:29`'s `_key_allowed()`, which allows them through because the policy lists them.
- **Why load-bearing:** Confirmed, live violation of two Critical Rules at once: "Names are metadata only — never included in behavior hashes" (`vco.template_name`) and the Phase-2 invariant "`sig_hash` is authoritative and UID-free by contract" (`vco.template_element_id`/`vco.template_unique_id`). Two category-override records that differ *only* in which view template they're attached to (name, ElementId, or UniqueId) but are otherwise behaviorally identical get *different* policy-reconstructed sig_hashes from `tools/run_extract_all.py`'s `sig_hash` stage — naming/UID noise can fragment what should be one identity cluster into many. `vco.vg_category_type`/`vco.include_controlled` remain declared-in-policy-but-never-emitted (dead, harmless — genuinely absent from the code under any name, unaffected by the canonicalization question) — the one piece of the original write-up that stands unchanged.
- **Confidence:** high (directly traced through the actual extraction-time code path, not inferred).

### 2. Retraction — `vco.category_hidden`/`vco.cut.*` omission from `allowed_items` is NOT a hash-correctness bug
- **What this audit originally claimed (2026-09-09, since retracted):** `vco.category_hidden` isn't individually listed in either partition's `allowed_items`, and `vco.cut.*` is absent from `view_category_overrides_annotation.allowed_items` specifically (present for `_model`). This was originally written up as two separate "silent collapse of distinct states" fail-soft violations.
- **Why that's wrong:** a PR review comment (`chatgpt-codex-connector`, PR #484) pointed out the missing piece, verified directly against `domains/view_category_overrides_model.py:253-259` and `_annotation.py:210-216`: both partitions compute `vco.override_properties_hash` as an MD5 rollup (`_compute_override_properties_hash`-equivalent inline logic) over every non-default, non-baseline `vco.*` item on the record — including the category's `hidden_item` whenever `category_hidden` is true, and including `cut_items` whenever any cut-graphics override differs from its default. `vco.override_properties_hash` is declared in **both** `allowed_items` and `required_items` for both partitions (confirmed by direct read of `policies/domain_sig_hash_policies.json`). So two records differing only in hidden-state or cut-properties get *different* `vco.override_properties_hash` values and therefore *different* policy-reconstructed sig_hashes — no collapse occurs. The original Findings 1a/1b are retracted.
- **Residual, much lower-severity observation:** `allowed_items` is inconsistent in *how* it exposes the override surface — `vco.projection.*`/`vco.halftone`/`vco.transparency` (and, for `_model` only, `vco.cut.*`) are enumerated both individually AND implicitly via the `override_properties_hash` rollup, while `vco.category_hidden` (both partitions) and `vco.cut.*` (`_annotation` only) are covered ONLY via the rollup. This makes the policy harder to audit field-by-field — a reader scanning `allowed_items` would not see `category_hidden` listed and might wrongly assume it's unhashed — but has no hash-correctness consequence. Documentation-clarity nit, not a bug.
- **Confidence:** high (both the retraction and the residual observation are directly traced).

### 5. Schema-version note — `.v1` correctly labels the current (buggy) preimage; the `.v2` bump belongs to Finding 1's fix, not a separate pre-existing gap
- **Correction (per PR review, chatgpt-codex-connector):** this audit originally wrote up `view_category_overrides_model`/`_annotation`'s `sig_hash_schema` staying at `.v1` as itself a stale-and-unflagged gap alongside Finding 1. That's backwards. Per D-045's own stated purpose (the `wall_types`/`object_styles_*` `.v1`→`.v2` precedent, `DECISIONS.md` lines ~2293-2300): a schema-version bump exists specifically so a `sig_hash` value's preimage definition can be identified *after* a hash-breaking correction ships — it distinguishes "value computed under the old preimage" from "value computed under the new one." D-045 bumped `wall_types`/`object_styles_*` to `.v2` only *after* D-039/D-042 actually narrowed those domains' preimages; bumping first would have falsely marked identical (still-buggy) definitions as incompatible across an export boundary that didn't exist yet. No preimage correction has shipped for `view_category_overrides_*` (Finding 1 is still open) — every existing reconstruction uses the same one (buggy) definition — so `.v1` is currently the *correct*, accurate label for that single definition, not evidence of neglect.
- **What's actually still true and worth carrying forward:** the schema bump is a required *part* of fixing Finding 1, not an independently-outstanding gap. Whoever removes `vco.template_name`/`vco.template_element_id`/`vco.template_unique_id`/`vco.context_type` (and the dead `vco.vg_category_type`/`vco.include_controlled` entries) from `allowed_items` should bump `sig_hash_schema` to `.v2` for both partitions in that same change, with a D-039/D-042/D-045-style reconciliation note — not as a separate follow-up.
- **Confidence:** high (directly grounded in D-045's own documented rationale, not inferred).
